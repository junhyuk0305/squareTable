## Finding B — loadProfile 읽기 실패 위장 (§4.8·§4.10) — 본 감사에서 수정
- **불일치 계층**: 스토어(loadProfile). supabase-js는 쿼리 에러를 throw 않고 `{error}`로 반환 → loadProfile이 `error`를 버려 profile=null로 흐름.
- **실패 시나리오**: 세션 중 access token 만료·5xx·429로 profiles select가 error 반환 →
  role 기본 'junior'·unit_id ''·pending '' 인 **빈 신원**이 `signed_in`으로 세팅.
  ① 사장 → owner 가드가 '가게 만들기'로 튕김(멀쩡한 매장 두고 재생성 유도).
  ② 승인 대기 직원 → 20초 폴링(refreshMembership→loadProfile) 중 1회 실패에 pendingUnitId 유실 → 대기화면이 join 화면으로 되돌아감.
- **근본 처방(적용)**: profiles select의 `error`를 포착 → 읽기 실패는 절대 "빈 상태=정상"으로 위장하지 않는다.
  · 이미 확립된 같은 사용자 세션이면 상태 **보존**(폴링/재시도로 복구) — 무음 강등 차단.
  · 콜드 로드면 가짜 테넌트 대신 깨끗한 `signed_out`(재로그인 복구).
  · `reportError('session.loadProfile.read')`로 관측(무음 아님).
- **핫존**: useSessionStore.ts **clean** → loadProfile 함수 단위 수정만.
- **잔여 리스크(고지)**: units/unit_subscriptions select error는 동일 패턴이나 심각도 낮음(unitId는 이미 확정=테넌트 누출 없음, subStatus는 fail-open 'none'). 본 수정은 신원 결정 read(profiles)에 집중. 본인측 db.ts 이전(A) 시 함께 흡수 권장.
- **회귀 가드(✅ 해소)**: 보존/리셋 판정을 순수함수 `sessionReadFailAction`(src/lib/store/sessionReadFail.ts)로 분리하고 `npm run qa:session`(scripts/qa-session-readfail.mjs, Node24 type-strip, 의존성 0)이 진리표를 고정 — 누가 error 무시로 되돌리면 즉시 FAIL. (client-state 로직이라 실 백엔드 qa로는 못 잡는 갭을 순수함수 단위 회귀로 커버.)
