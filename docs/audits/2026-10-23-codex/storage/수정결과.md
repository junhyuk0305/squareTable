# STOR-01 수정과 검증

제품 변경은 `src/lib/store/useAttendanceStore.ts` 한 파일이다. 기존 감사 원본과 재현 스크립트는 보존했다. 다른 작업자의 TimesheetView, 급여, db.ts, 기존 하니스는 수정하지 않았다.

## 바뀐 동작

수정 실패는 해당 요청이 넣었던 객체가 그대로 남아 있을 때만 되돌린다. 이후 저장이나 재조회로 바뀐 객체는 과거 값으로 덮지 않는다. 삭제 실패는 같은 ID가 이미 있다면 다시 삽입하지 않는다. 자동 출근과 퇴근도 같은 실패 복구 경계를 사용한다.

같은 기록의 요청이 모두 끝나고 실패가 있었다면 해당 직원의 해당 월을 조회한다. 월 조회는 오래된 기록을 찾기 위한 범위다. 실제로 바꾸는 것은 실패한 ID 한 행뿐이다. 다른 기록은 유지한다.

복구 조회를 시작한 뒤 새 저장 요청이 생기면 요청 버전이 달라진다. 이 경우 이전 복구 응답을 버린다. 실시간 조회로 행 객체가 바뀌어도 오래된 복구 응답을 버린다. 계정이나 매장 세대가 달라진 뒤에는 롤백과 복구를 적용하지 않는다.

두 저장이 모두 실패한 경우도 검사했다. 단순 객체 일치 검사만으로 끝내면 두 번째 실패가 첫 번째 실패의 낙관적 값을 되살릴 수 있다. 그래서 모든 같은 행 쓰기가 끝난 후 서버를 확인하는 단계가 필요하다.

## 제한과 실기기 확인

운영 요청, 공유 DB 변경, 발송, 배포, 커밋은 하지 않았다. DB 계약 변경이 없으므로 구형 앱의 호출 방식은 바뀌지 않는다. 이번 수정의 효력은 수정 버전을 배포한 클라이언트에만 생긴다.

실제 Android/iOS 화면에서 출퇴근 기록 수기 수정을 빠르게 두 번 저장하고 첫 요청만 실패시키는 확인이 남아 있다. 최신 성공 시간이 유지돼야 한다. 삭제 대기 중 재조회와 늦은 실패에서도 같은 기록이 두 번 나타나면 안 된다.

복구 조회 자체가 실패하면 서버 상태를 확인할 수 없다. 기존 읽기 오류 안내와 다음 성공 재조회가 필요하다. 이 검사에서 실제 네트워크 발생률이나 운영 데이터 손실을 측정하지 않았다. 요청 실패 후 입력창 보존은 TimesheetView 범위이므로 이번 변경에 포함하지 않았다.
