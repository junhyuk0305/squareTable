# JOURNEY-01 수정 및 검증

제품 수정은 `src/lib/push/nativepush.ts` 한 파일이다. `useSessionStore`, 서버, DB, 기존 하니스는 수정하지 않았다. 다른 작업자의 변경을 되돌리지 않았다.

## 바뀐 동작

초기 연결 실패 또는 재로그인 대기 중 받은 알림을 메모리에 보관한다. 인증이 확인되고 기존 500ms 화면 전환 대기가 끝나면 해당 목적지로 한 번 이동한다. 콜드 스타트 응답과 알림 리스너가 같은 탭을 전달해도 중복 이동하지 않는다. 지연된 초기 조회보다 나중에 직접 누른 알림을 우선한다.

기존 명시적 로그아웃 경로의 `clearDeviceNotifications`는 대기 알림과 OS의 마지막 응답도 버린다. 확인된 사용자 ID가 바뀌면 이전 대기와 지연 응답을 취소한다. 옛 푸시의 메타데이터 조회나 매장 진입 모듈을 기다리는 동안 계정이 바뀌어도 이전 이동을 실행하지 않는다. 새 계정 로그인 뒤 새로 누른 알림은 동작한다.

## 검증

같은 정상 기대 테스트를 수정 전 소스와 수정 후 소스에 실행했다.

| 기준 | 통과 | 실패 |
|---|---:|---:|
| 수정 전 원본 | 14 | 20 |
| 수정 후 | 34 | 0 |

Android와 iOS 분기 각각 17사례다. 실제 제품 모듈, `pushTap`, 역할 변환, 알림 레지스트리를 실행한다. 네이티브 알림 API, 세션, 타이머, 라우터, 매장 진입은 대역이다. 실제 네트워크, OS 알림, 화면 렌더 검사는 아니다.

정상 콜드 스타트, 연결 복구, 수동 재로그인, 인증 전 알림, 중복 탭, 명시적 로그아웃, 계정 전환, 빈 알림, 외부 URL 거부, 새 로그인 후 새 알림, 늦은 OS 응답, 늦은 옛 알림 조회, 같은 계정 복구, 다른 계정 차단, 최신 탭 우선, 다른 매장 진입, 매장 진입 대기 중 계정 전환을 검사했다.

실행 파일은 `test-push-recovery.cjs`다. `red.json`과 `green.json`에 사례별 결과 및 실행 소스 SHA-256을 기록했다. 원래 감사 재현 파일은 보존했다. `nativepush.before.ts.txt`, `nativepush.after.ts`, `nativepush.diff`, `file-evidence.json`, `baseline-head.txt`로 수정 범위와 기준을 남겼다. 통합 타입 검사와 린트는 부모 담당자가 수행한다.

Expo SDK 56의 [Notifications 공식 문서](https://docs.expo.dev/versions/v56.0.0/sdk/notifications/)에서 초기 응답 조회, 응답 리스너, 응답 초기화 API를 확인했다. 새 API나 새 서버 필드를 도입하지 않았다.

## 남은 확인과 제한

- Android 및 iOS에서 배정 알림을 눌러 앱 시작 → 초기 연결 실패 → 다시 연결 → 원래 업무 열림을 확인한다.
- 두 앱에서 초기 로그인 화면 → 로그인 → 원래 업무 열림을 확인한다.
- 연결 실패 화면의 다른 계정 로그인 동작 또는 명시적 로그아웃 뒤 B로 로그인했을 때 A의 목적지가 자동으로 열리지 않아야 한다. B에게 온 새 알림은 열려야 한다.
- 다른 매장 알림은 매장 진입 뒤 원래 항목으로 가야 한다. OS의 콜드 스타트 응답 순서와 실제 라우터 안정화는 실기기 확인이 필요하다.
- 수신자 ID가 없는 기존 알림만으로 첫 부팅 이전의 수신 계정을 역으로 식별할 수는 없다. 이번 경계는 앱에서 확인한 사용자 전환과 기존 명시적 로그아웃 정리에 근거한다. 서버 권한 검사는 기존대로 유지한다.
- 대기 정보는 이번 실행 메모리에만 있다. 앱 강제 종료 중 새 복구 기능을 추가하지 않았다. 구형 앱은 이 수정이 포함된 버전으로 업데이트해야 한다.

운영 호출, 실제 발송, 계정 생성, 배포, 커밋은 하지 않았다. 독립 검토와 실제 기기 확인 전 전체 완료로 판정하지 않는다.
